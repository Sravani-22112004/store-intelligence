# CHOICES.md — Engineering Decision Log

## Decision 1 — Detection Model: YOLOv8n + Custom IoU Tracker

### Options Considered

| Option | Pros | Cons |
|--------|------|------|
| YOLOv8n | Fast, well-documented, pretrained on COCO (includes person class), runs on CPU | Nano model has lower accuracy than larger variants |
| YOLOv8m/l | Higher accuracy | 3-5x slower inference, not needed for 15fps footage |
| RT-DETR | Transformer-based, strong on occlusion | Much heavier, harder to deploy without GPU |
| MediaPipe | Very fast | Optimised for single-person, poor for crowded scenes |
| ByteTrack (full) | State-of-the-art multi-object tracking | Requires `lap` library which has complex build deps on ARM Mac |

### What AI Suggested

Claude suggested using YOLOv8m (medium) + ByteTrack for "production-grade accuracy." It also suggested using a VLM (GPT-4V) for zone classification by sending cropped frame regions to classify which zone a person is in.

### What I Chose and Why

**YOLOv8n + custom IoU tracker.**

The nano model processes a 1080p frame in ~40ms on CPU, meaning we can handle 15fps footage with frame-skipping (every 3rd frame). The medium model would be 3x slower and push processing time well beyond real-time without a GPU.

For tracking, I implemented a custom IoU+centroid matcher instead of ByteTrack. This was a pragmatic call: ByteTrack's `lap` dependency fails on Apple Silicon in many configurations, and a clean IoU tracker covers the same core matching logic for this problem. The tracker handles:
- **Group entry**: Each bounding box gets its own track, so 3 people entering simultaneously produce 3 `ENTRY` events.
- **Re-entry**: Lost tracks are buffered for 5 minutes; returning centroids reuse the original `visitor_id`.
- **Partial occlusion**: IoU matching degrades gracefully — low IoU means higher miss counter, not a crash. Confidence score is preserved.

On the VLM zone classification: I tested sending frame crops to a vision model for zone ID. It worked but added ~800ms latency per crop and ~$0.02/frame in API costs — completely unviable for 20-minute clips at 15fps. Rule-based zone assignment (centroid inside zone bounding box from `store_layout.json`) is instant, deterministic, and correct for fixed-camera footage. VLM is useful for the *initial* task of inferring zone boundaries from footage when no layout JSON is provided — I would use it there, but not per-frame.

## Decision 2 — Event Schema Design

### Options Considered

**Option A: Flat schema** — all fields at top level, no `metadata` object.  
**Option B: Nested metadata** — core fields flat, event-specific data in `metadata` object (chosen).  
**Option C: Polymorphic schema** — separate schema per event type (e.g., `EntryEvent`, `ZoneDwellEvent`).

### What AI Suggested

Claude suggested Option A (flat schema) for "simplicity and easier SQL querying." It also suggested dropping `confidence` from events with confidence > 0.8 to "reduce noise."

### What I Chose and Why

**Option B — nested metadata.**

Flat schemas become unmaintainable when event types differ significantly in their fields. A `BILLING_QUEUE_JOIN` needs `queue_depth`; a `ZONE_DWELL` needs `dwell_ms`; an `ENTRY` needs neither. Putting all these at top level creates a sparse, wide table. The `metadata` JSON column absorbs event-specific fields cleanly.

I rejected Option C (polymorphic) because the ingestion endpoint receives mixed event types in a single batch — a single Pydantic model with a discriminated union adds serialisation complexity for minimal benefit.

On dropping confidence: I disagreed with AI here. The problem statement explicitly says "do not suppress low-confidence events." More importantly, if we drop low-confidence events at the pipeline layer, we permanently lose that signal. The API consumer (or a downstream ML model) can apply a confidence threshold. We cannot un-drop data. Every event is emitted with its actual confidence score, even 0.4.

**Key schema choices I made independently:**
- `dwell_ms` as integer milliseconds, not float seconds — avoids floating point precision drift in SQL `AVG()`
- `is_staff` as first-class boolean field, not in metadata — every analytics query filters on it; it belongs at the top level
- `session_seq` as an ordinal counter per visitor session — enables session replay for debugging without storing full video segments
- `event_id` as UUID v4 generated by the pipeline — makes the ingest endpoint idempotent by design

## Decision 3 — API Storage Architecture

### Options Considered

| Option | Write Performance | Query Performance | Complexity |
|--------|------------------|-------------------|------------|
| SQLite | Moderate | Good for single-node | Minimal |
| PostgreSQL | High | Excellent with indexes | Low |
| PostgreSQL + Redis Streams | Very High | Excellent | Medium |
| TimescaleDB | Very High | Excellent for time-series | Medium-high |

### What AI Suggested

Claude recommended a Redis Streams + PostgreSQL hybrid: Redis for ingest (high write throughput), with a consumer process flushing to PostgreSQL for analytics queries. It argued this would "scale to 40 stores easily."

### What I Chose and Why

**PostgreSQL with composite indexes, no Redis.**

For the challenge scope (5 stores, 20-minute clips), Redis adds operational complexity without changing correctness. The ingest path writes events in batches of up to 500; at 15fps with frame-skipping, a single store generates roughly 2-5 events/second. PostgreSQL with a connection pool handles this comfortably.

I added two composite indexes that cover every analytics query:
- `(store_id, timestamp)` — covers all time-range queries
- `(store_id, visitor_id)` — covers session deduplication in funnel

**Where I agree with AI on Redis:** At 40 live stores sending events simultaneously, the ingest endpoint would receive ~200 events/second. PostgreSQL without write batching would struggle. Redis Streams as an ingest buffer, with a background consumer flushing to PostgreSQL, is the right architecture at that scale. I document this in DESIGN.md as the natural next evolution. For this submission, the simpler architecture is appropriate and honest about its limits.

**No pre-aggregation:** Metrics are computed in real time from raw events. Pre-aggregated summary tables would speed up dashboard queries but complicate re-entry deduplication (a visitor's session can span multiple aggregation windows). Real-time SQL on indexed tables is fast enough for the current data volume.

## Summary

| Decision | AI Suggested | I Chose | Why I Diverged |
|----------|-------------|---------|----------------|
| Detection model | YOLOv8m + ByteTrack | YOLOv8n + custom tracker | Speed + portability on CPU/ARM |
| VLM zone classification | Per-frame VLM crops | Rule-based bbox lookup | 800ms latency + cost per frame |
| Confidence filtering | Drop events < 0.5 | Always emit with actual confidence | Cannot un-drop data; consumer decides threshold |
| Schema style | Flat all-fields | Nested metadata object | Sparse wide table is unmaintainable |
| Storage | Redis + PostgreSQL | PostgreSQL only | Correct for this scale; Redis documented as next step |
| Re-entry window | 10 minutes | 5 minutes | Tighter window = fewer false positives near entrance |
